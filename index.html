Connect Tiara to your GitHub

Your board lives safely in your own GitHub account. Connect it once and you never download anything again - just visit this page.

  1. Open github.com/settings/tokens → Generate new token (classic).
  2. Name it "Tiara", then tick just two boxes: repo and project.
    repo = read/write your issues + board data · project = drive the GitHub boards
  3. Click Generate token and copy it (starts with ghp_…).
  4. Paste it below and press Connect.

Change process · the full journey of one change

1 The one rule

Nothing is finished until two things are true:

  • the gate comes back green (make verify)
  • the change works in the app on a phone (watched on a real device)

2 The gate

Every change goes through one command, make verify. It runs four quick checks in order, cheapest first, so a problem surfaces in two seconds instead of after a long build:

  • Tidy (swiftformat): the code is re-formatted to the house style, so spacing is never an argument.
  • Rules (swiftlint --strict): the things formatting can't check: no banned patterns, no stray colours or magic numbers, no forbidden shortcuts.
  • Build (xcodegen + xcodebuild): the app compiles.
  • Test (Swift Testing + XCUITest): the tests run.

All four passing is the moment a change is allowed to exist. If any one fails, the change is simply not done yet.

3 The safety nets underneath

Three guards keep the gate honest:

  • The push leash (guard-bash.sh + the .verify-pass fingerprint): the automated helper cannot send code to GitHub unless the gate passed on exactly that code. The leash applies only to code edited and pushed by AI, never to a person at the keyboard.
  • The canary (scripts/gate-canary.sh): every so often a test is deliberately broken to confirm the gate still catches it. A gate that cannot fail is worthless, so it is proven, on purpose.
  • No surprises from time or chance (an injected Now clock + SeededRandomNumberGenerator): tests run on a fixed clock and fixed dice, so a test never passes one day and fails the next for no reason.

4 The deeper checks, run on demand

Beyond the quick gate sit heavier checks, each on its own, run when the relevant area changes:

  • Concurrency (make tsan, Thread Sanitizer): hunts for the bug where two things happen at once and collide.
  • Accessibility (make a11y: a WCAG contrast test + performAccessibilityAudit): confirms text has enough contrast and the screen works with assistive tools. Text must also grow when the system font size is raised (Dynamic Type); that one is a firm rule for every app. These findings are a to-do list, not a blocked build (advisory vs. blocker).
  • Design snapshots (make snapshot, ImageRenderer pixel checks): confirm the colours and components still match how they were defined, so nothing quietly drifts to grey.
  • Deep correctness (property tests + API contract tests): extra tests that hammer the important logic across many combinations, plus a check that any API still answers in the shape the app expects.
  • Speed (make perf, XCTest measure): measures how fast the heavy paths run, so a slowdown shows as a trend.

5 Why almost nothing runs in the cloud automatically

Quick tests can run locally and frequently. The cloud (Xcode Cloud) has one job: a clean-room second opinion, building the app from scratch the way a brand-new computer would, to catch the "worked on one machine" surprises. It runs only when triggered by an increase in build number in the config file (CURRENT_PROJECT_VERSION in Config/Version.xcconfig).

6 Shipping to testers

Changing one number, the build number (CURRENT_PROJECT_VERSION in Config/Version.xcconfig), and pushing is the only thing that triggers a release. That, and nothing else, tells the cloud to build the app, sign it, and hand it to TestFlight (Xcode Cloud archive plus TestFlight deploy). Ordinary commits never ship. Shipping is a deliberate, one-number act, and not every app needs it: it is opt-in (marked by release.yml).

7 How every app is born with all of this

None of this is set up by hand per app. One command (newapp, from the factory template) stamps out a new app that already carries the gate, the safety nets, the deeper checks, the dev-and-real split (separate DEV and PROD schemes, bundle ids, and CloudKit containers), and the written-down rules (the ADRs). Every app inherits the whole machine on day one, so quality is never bolted on later during a scary audit. The Compliance tab shows, at a glance, how far along each app is across all of it.

How the factory checks itself · the four couplings

Every rule in this factory has the same failure mode. Something is set up correctly, works for a while, and then quietly stops, because nothing was ever going to notice that it had. The version stamp was bumped six times in two days and then sat still for seventeen template changes. A gate can be installed and never fire. An explanation can be written and then describe a check that no longer works that way.

The answer is not discipline. It is coupling: tying two things together so that moving one without the other is visible. Four such pairs matter here. Three exist. The fourth is named honestly as missing rather than left to be discovered.

Solid lines are couplings that exist and are checked every four hours. The dashed line is the one that does not.

1 The template to its own version number

The factory has a version, in FACTORY_VERSION. It was bumped from 1 to 6 in two days, once per real change, and then stopped while template/ went on changing seventeen more times: the finish gate, the enforcement manifest, the scope guards, and the whole queue-file removal all landed under a number that still said 6.

What catches it now. Every scan counts the commits to template/ since the version last moved. Zero means the number describes the factory. Anything above zero means the factory has run ahead of its own version, and the compliance view says by how much. Nothing in _bootstrap can fail a build, because it has no Makefile, no verify and no hooks, so this is enforced where you actually look rather than in a terminal nobody opens.

2 The factory to each app

Each app records the factory version it was built from, in .factory-version. On its own that is a number nobody reads. Compared against the factory's current version it becomes the answer to a real question: how far behind is this app, and by how much.

What catches it now. Two checks in the Bootstrap dimension. factory_stamped asks whether the app declares a version at all. factory_current asks whether that version is the current one. An app stamped 6 against a factory at 7 is behind by a known amount instead of by an unknown one.

The fix for a failing factory_current is to bring the app up to date and then bump the file. Writing the number without doing the work is exactly how the stamp became a lie the first time.

3 A check to its explanation

Every compliance check carries four fields: what it means, how it is decided, how to see it for yourself, and how to get to green. An explanation that is present but no longer true is worse than a missing one, because the board still looks complete.

What catches it now. The slice of compliance.mjs that implements each check is hashed and recorded in compliance-explain.lock.json. Change how a check decides without re-reading its explanation and the next scan says so, on the board, above the legend. Re-locking is a separate deliberate command and is meant to be its own commit, because it is you stating that you re-read the check and the explanation still holds.

4 The factory to the checks · this one does not exist

Nothing makes a check appear when the factory gains a capability. The checks are written by hand, so the template can grow a rule and the board will never mention it, and nothing flags the gap.

This is not hypothetical. template/scripts/conform.sh is the script that stops queue files coming back, and there is no check that it is installed at all. An app could be missing it entirely and the board would say nothing. The same is true of the enforcement manifest and of tree-fingerprint.sh.

So coupling 1 catches the factory changing. It does not catch the checks failing to follow. Closing that would take the same shape one level up: record a hash of template/ beside the factory version, and when the template moves, require either a check to move with it or an explicit note that none was needed. The cost is that every template change then costs a deliberate line, which is precisely what stopped happening after version 6.

5 The shape all four share

Each one takes a thing that can quietly go stale and ties it to a thing that moves, so that the gap between them is a number rather than a feeling. Then it puts that number somewhere it is seen without being sought.

That last part is the load-bearing half. A check that writes to a log nobody opens is not a check, it is a diary. Every one of these reports into the compliance view, on the same four hourly refresh as everything else, which means the question "is this still true" is answered continuously instead of during a scary audit.
